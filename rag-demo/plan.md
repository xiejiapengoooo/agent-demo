# MinerU + FAISS 多模态 PDF RAG 实施计划

## 1. 目标

基于当前项目已有的 MinerU、BGE-M3 和 FAISS，实现一套能够处理以下内容的 PDF RAG：

- 普通正文、标题、列表和跨页段落；
- 普通表格、复杂表格和跨页表格；
- PDF 中的图片、扫描图、流程图和图表；
- 表格中的精确数字查询、比较和计算；
- 回答结果携带文档、章节、页码范围和内容位置。

本计划以解析准确性、检索可控性和引用可追溯性为优先目标。

## 2. 已确定的约束

1. 不做增量处理。
2. 每次构建都清空旧的 MinerU 输出、标准化数据和 FAISS 索引，然后处理 `source/` 下的全部 PDF。
3. 不创建 `tests/` 目录，不引入单元测试或集成测试模块。
4. 保留构建时数据校验；校验属于生产构建流程，用于阻止错误数据进入索引，不属于测试模块。
5. MinerU 是 PDF 解析入口，FAISS 是主要向量索引。
6. BGE-M3 继续作为文本向量模型。
7. 表格、正文和图片分别处理，不再先拼成整页后统一切块。

## 3. 当前实现的问题

当前 `vec.py` 的处理方式是：

```text
MinerU block
  -> 按页面拼接全部内容
  -> 每页按 500 token 切块
  -> 写入一个 LangChain FAISS 索引
```

这种方式存在以下问题：

- 正文、表格和图片使用同一种切块策略；
- HTML 表格被转换成文本后，`rowspan`、`colspan` 和表头层级丢失；
- 跨页表格只能记录首页，不能准确记录结束页和每页 bbox；
- 跨页段落会在页边界被截断；
- 图片路径、图片标题、OCR 和周围正文没有形成完整关联；
- 单一向量召回不擅长匹配金额、编号、表头和短关键词；
- LangChain FAISS 默认距离的含义容易与相似度混淆；
- 检索命中子片段后，无法恢复完整表格、脚注或图片。

当前示例 PDF 的第 3-4 页是一张跨页表格。MinerU 3.4.5 将合并后的 HTML 放在第 3 页，并在第 4 页留下空表格占位。因此需要同时读取 `content_list_v2.json` 和 `middle.json`，恢复正确的跨页范围。

## 4. 总体架构

```text
PDF 文件
  -> MinerU 全量解析
  -> MinerU 输出适配器
  -> 统一文档元素模型
  -> 文档结构恢复
       - 章节层级
       - 跨页段落
       - 跨页表格
       - 图片与标题/正文关联
  -> 父对象存储
  -> 检索子块生成
  -> BGE-M3 向量化
  -> text/table/figure 三个 FAISS 索引
  -> SQLite 元数据及全文检索
  -> 多路召回和 RRF 融合
  -> Reranker 重排
  -> 父级上下文恢复
  -> LLM/VLM 回答
  -> 文档名、章节、页码和 bbox 引用
```

## 5. 目标目录结构

```text

│   ├── children.jsonl            # 用于索引的检索子块

│   ├── figure.faiss              # 图片文字代理向量索引
│   └── metadata.sqlite           # 父子对象、引用信息和 FTS5
├── config.py                     # 路径、模型和检索参数
├── models.py                     # 标准数据模型
├── mineru_parser.py              # MinerU 输出读取与适配

```

不创建 `tests/` 目录。

## 6. 全量覆盖构建流程

构建入口：

```bash
uv run python rag-demo/build_index.py
```

每次构建严格执行：

1. 确认 `source/` 中至少存在一个 PDF。
2. 删除并重建 `mineru-output/`。
3. 删除并重建 `normalized/`。
4. 删除并重建 `db/`。
5. 对 `source/` 下全部 PDF 运行 MinerU。
6. 读取每份 PDF 对应的 `*_content_list_v2.json`。
7. 同时读取 `*_middle.json`，补充跨页和底层版面信息。
8. 建立统一父对象。
9. 恢复章节、跨页段落和跨页表格。
10. 生成正文、表格和图片检索子块。
11. 将父子对象写入 SQLite 和 JSONL。
12. 使用 BGE-M3 批量生成归一化向量。
13. 全量生成三个 FAISS 索引。
14. 执行构建时强制校验。
15. 生成 `build_report.json`。

构建过程发生不可恢复的数据错误时直接失败，不保留不完整的新索引。

## 7. 统一数据模型

### 7.1 父对象

父对象代表完整的语义单元，负责保存生成答案所需的全部上下文。

```json
{
  "parent_id": "doc01_table_003",
  "document_id": "doc01",
  "type": "text|table|figure",
  "section_path": ["第四章 个人业绩考核标准"],
  "page_start": 3,
  "page_end": 4,
  "bbox_by_page": {
    "3": [147, 782, 942, 913],
    "4": [146, 78, 944, 662]
  },
  "title": "个人业绩考核标准",
  "content": {},
  "source_path": "source/example.pdf",
  "parse_status": "ok|repaired|needs_review"
}
```

不同类型的 `content`：

- `text`：原始文本、合并后的文本、标题级别和前后元素关系；
- `table`：原始 HTML、规范化二维数据、表头、数据行、标题和脚注；
- `figure`：图片路径、caption、OCR、视觉描述和附近正文。

### 7.2 检索子块

子块只负责召回，通过 `parent_id` 指向完整父对象。

```json
{
  "child_id": 1024,
  "parent_id": "doc01_table_003",
  "document_id": "doc01",
  "type": "table_row",
  "search_text": "...",
  "page_start": 3,
  "page_end": 4,
  "ordinal": 2
}
```

`child_id` 使用全局连续整数，作为 FAISS 向量位置与 SQLite 记录之间的稳定映射。

## 8. MinerU 输出读取

### 8.1 主数据源

使用 `*_content_list_v2.json` 获取：

- 元素类型；
- 文本内容；
- 表格 HTML、标题和脚注；
- 图片路径；
- 页内 bbox；
- 标题层级。

### 8.2 辅助数据源

使用 `*_middle.json` 获取：

- `cross_page` 标记；
- 空表格占位与主表格之间的关系；
- 更细的 block、line 和 span 信息；
- 页面尺寸；
- MinerU 中间解析状态。

Markdown 仅用于人工排查，不作为索引主数据源，因为它不能稳定保留跨页来源和 bbox。

## 9. 文档结构恢复

### 9.1 章节层级

按照标题的 `level` 维护章节栈：

```text
一级标题 -> 二级标题 -> 三级标题 -> 当前正文/表格/图片
```

每个父对象记录完整 `section_path`。检索文本中需要加入章节路径，以提升短标题和同名内容的区分能力。

### 9.2 跨页段落

满足以下条件时，将前一页最后一个正文块与下一页第一个正文块合并：

- 前一个 block 靠近页底；
- 后一个 block 靠近页顶；
- 两者都是正文类型；
- 中间没有新标题或新章节；
- 前一段没有明显结束符；
- 后一段不像新条款、新列表或新标题。

合并结果必须保留两页 bbox，设置正确的 `page_start` 和 `page_end`。

如果规则置信度不足，不自动合并；分别建块，并在 `build_report.json` 中记录警告。

## 10. 表格处理

### 10.1 HTML 规范化

不能继续使用简单 HTML 文本提取。需要：

1. 解析 `<tr>`、`<td>` 和 `<th>`；
2. 展开 `rowspan` 和 `colspan`；
3. 构造固定列数的二维矩阵；
4. 识别多级表头；
5. 对跨行的类别值执行向下填充；
6. 保留空单元格，不随意删除；
7. 分离表格标题、表体和脚注；
8. 同时保留原始 HTML，以便复核。

### 10.2 跨页表格识别

按以下优先级处理：

1. `middle.json` 中存在 `cross_page` 标记时，优先采用 MinerU 的跨页关系。
2. 上一页底部是表格且下一页顶部是表格时，建立跨页候选。
3. 比较两页表格的横向位置、宽度、列数、表头和所在章节。
4. 结合“续表”“continued”等文本信号确认。

默认几何阈值：

```text
上一页表格底部位置 >= 页面高度的 80%
下一页表格顶部位置 <= 页面高度的 20%
横向重叠比例 >= 85%
宽度差异 <= 10%
```

阈值放在 `config.py` 中统一配置。

### 10.3 跨页表格合并场景

场景 A：前页 HTML 完整，后页为空占位。

- 判断 MinerU 是否已将后页数据合并到前页 HTML；
- 保留前页完整 HTML；
- 后页空 block 不单独建索引；
- 父表格设置完整页码范围和每页 bbox；
- `parse_status` 设为 `repaired`。

场景 B：前后页都有 HTML。

- 分别规范化为二维矩阵；
- 删除后页重复表头；
- 按行纵向合并；
- 保留原始分页行号；
- 校验合并前后列数一致。

场景 C：主表或续表 HTML 为空，且无法从相邻页恢复。

- 从原 PDF 按 bbox 渲染表格区域；
- 使用 OCR 或视觉模型重新识别；
- 识别成功后标记 `repaired`；
- 仍然失败则终止构建，避免静默漏掉表格数据。

### 10.4 表格父子块

父块保存完整表格。子块每 3-8 个数据行一组，并重复：

- 章节路径；
- 表格标题；
- 完整列名；
- 单位；
- 与当前行相关的脚注；
- 页码范围。

示例检索文本：

```text
章节：第四章 个人业绩考核标准。
表格：个人业绩考核标准；页码：3-4。
列：类别、行员级别、考核分值、储蓄业务、个贷业务、卡业务。
数据：类别=高级客户经理；行员级别=5；考核分值=140；
储蓄业务=500万；个贷业务=800万。
```

完整表格较小时，可额外生成一条表格摘要子块，但不能用摘要替代表格行块。

## 11. 图片处理

### 11.1 图片父对象

每张图片保存：

- MinerU 图片路径或从 PDF 裁剪后的图片路径；
- 页码和 bbox；
- 图片标题；
- 图片脚注；
- 图片内部 OCR；
- 前后相邻正文；
- 可选的视觉模型描述。

### 11.2 图片检索文本

BGE-M3 只索引图片的文字代理：

```text
章节路径 + 图片标题 + 图片脚注 + OCR + 视觉描述 + 附近正文
```

这些内容写入 `figure.faiss`。命中后必须通过父对象取得原图或 bbox 裁剪图。

### 11.3 图片问答

- 纯 OCR 问题可以由文本模型回答；
- 图表趋势、流程关系、图形位置等视觉问题，将图片交给 VLM；
- 如果图片缺少 caption 且 OCR 为空，必须生成视觉描述，否则该图片无法通过 BGE-M3 被有效召回；
- 表格图片进入表格处理流程，不作为普通图片处理。

## 12. 正文切块

正文不再按整页切分，改为按章节和自然段组织：

- 优先以标题、条款、段落和列表边界切分；
- 建议块大小为 350-700 token；
- 建议重叠为 50-100 token；
- 不跨章节进行重叠；
- 短标题与其后的第一段合并生成检索子块；
- 跨页但语义连续的段落先合并，再切块。

父对象仍保存完整条款或完整段落，切块只作用于检索子块。

## 13. 存储设计

### 13.1 FAISS

建立三个独立索引：

| 索引 | 内容 | 向量模型 |
| --- | --- | --- |
| `text.faiss` | 标题、条款、正文 | BGE-M3 |
| `table.faiss` | 表格摘要和表格行块 | BGE-M3 |
| `figure.faiss` | caption、OCR 和视觉描述 | BGE-M3 |

所有 BGE-M3 向量进行 L2 归一化，FAISS 使用 `IndexFlatIP`。这样返回值就是内积相似度，数值越大越相似。

初期采用精确索引 `IndexFlatIP`，不使用 IVF/HNSW。只有文档规模导致检索延迟不可接受时，再单独评估近似索引。

### 13.2 SQLite

`metadata.sqlite` 至少包含：

```text
documents       文档信息
parents         完整父对象
children        检索子块及 FAISS 映射
table_rows      结构化表格行
assets          图片和裁剪资源
children_fts    SQLite FTS5 全文索引
```

SQLite 保存完整元数据和结构化内容，FAISS 不保存 Python pickle 对象，从而避免依赖 `allow_dangerous_deserialization=True`。

## 14. 检索流程

### 14.1 问题分类

先将问题分类为：

- `text`：制度、定义、职责和普通说明；
- `table`：数字、条件、行列比较和计算；
- `figure`：图片、图表、流程和视觉关系；
- `mixed`：需要多个模态共同回答。

分类可以先采用关键词规则，规则无法确定时同时检索多个索引。

### 14.2 多路召回

默认参数：

```python
TEXT_TOP_K = 20
TABLE_TOP_K = 20
FIGURE_TOP_K = 10
FTS_TOP_K = 20
RERANK_TOP_K = 8
```

召回路径：

```text
BGE-M3 Dense 召回
  + SQLite FTS5 精确召回
  -> RRF 融合
  -> 按 parent_id 去重
  -> Reranker 重排
```

FTS5 用于补充向量检索不稳定的内容：

- 金额和百分比；
- 条款编号；
- 产品型号和专有名词；
- 表头和短关键词。

### 14.3 重排

使用 `BAAI/bge-reranker-v2-m3` 对融合候选进行重排。

Reranker 输入为：

```text
(用户问题, 子块 search_text)
```

只对前 20-40 个融合候选重排，最终保留前 8 个，避免延迟过高。

### 14.4 父级上下文恢复

命中子块后，根据类型恢复上下文：

- 正文：完整条款、所属标题和必要的前后段落；
- 表格：表名、完整表头、命中行、相邻行、单位和脚注；
- 图片：caption、OCR、附近正文和原图；
- 跨页元素：完整 `page_start-page_end` 和各页 bbox。

同一父对象有多个子块命中时只加载一次。

## 15. 计算型问题

以下问题不得完全依赖 LLM 心算：

- 求和、平均值、最大值和最小值；
- 同比、环比和比例；
- 条件筛选和排序；
- 多行、多列比较；
- 单位换算。

处理流程：

```text
检索表格
  -> 从 SQLite 获取规范化 table_rows
  -> 识别相关列和筛选条件
  -> Python 执行计算
  -> 将计算结果和原始行共同交给 LLM 组织答案
```

原始值、解析后的数值和单位要分别保存，避免把“500万”直接丢失为无单位数字。

## 16. 回答生成与引用

传给模型的上下文保持结构化，不拼成无来源的大段文本：

```text
[证据 1]
文档：xxx.pdf
章节：第四章 个人业绩考核标准
页码：3-4
类型：table
内容：...

[证据 2]
文档：xxx.pdf
章节：第五章 工作质量考核标准
页码：5
类型：text
内容：...
```

生成规则：

1. 只根据已提供证据回答。
2. 表格计算必须使用计算模块返回的结果。
3. 图片视觉问题必须使用原图或裁剪图。
4. 证据不足时明确说明未找到，不允许补写。
5. 答案必须返回文档名、章节和页码范围。
6. 前端需要高亮来源时，同时返回 bbox。

推荐的结构化返回值：

```json
{
  "answer": "...",
  "citations": [
    {
      "document_id": "doc01",
      "source": "source/example.pdf",
      "page_start": 3,
      "page_end": 4,
      "bbox_by_page": {}
    }
  ],
  "evidence": [],
  "confidence": "high|medium|low"
}
```

## 17. 构建时强制校验

这些校验直接集成在 `build_index.py` 中，不创建测试模块。

构建失败条件：

- `source/` 没有 PDF；
- MinerU 未生成 `content_list_v2.json`；
- PDF 页数与 MinerU 页面数不一致；
- 出现无法关联或无法恢复的空表格；
- 表格规范化后各行列数不一致；
- 图片文件路径不存在；
- 子块引用不存在的父对象；
- FAISS 向量数量与 SQLite 对应记录数量不一致；
- 向量维度与索引维度不一致；
- `page_start > page_end`；
- 构建结果没有任何可检索子块。

警告但允许构建的情况：

- 跨页段落置信度不足，因此没有自动合并；
- 图片缺少 caption，但存在可用 OCR；
- 表格由回退识别恢复；
- 某个非关键 block 被 MinerU 标记为丢弃。

`build_report.json` 示例：

```json
{
  "documents": 1,
  "pages": 9,
  "parents": {
    "text": 35,
    "table": 1,
    "figure": 0
  },
  "children": {
    "text": 42,
    "table": 8,
    "figure": 0
  },
  "repaired_cross_page_tables": 1,
  "repaired_cross_page_paragraphs": 1,
  "warnings": [],
  "errors": []
}
```

## 18. 配置建议

`config.py` 集中保存：

```python
EMBED_MODEL_ID = "BAAI/bge-m3"
```

## 19. 命令行接口

```bash
uv run python rag-demo/build_index.py
```

纯检索调试：

```bash
uv run python rag-demo/search.py "高级客户经理的考核标准是什么"
```

完整问答：

```bash
uv run python rag-demo/rag.py "高级客户经理 5 级需要达到什么标准"
```

`search.py` 输出至少包含：

- 最终相关度；

- `child_id` 和 `parent_id`；
- 文档名；
- 章节；
- 页码范围；
- 检索子块；
- 恢复后的父级上下文摘要。

## 20. 实施阶段

### 阶段一：数据模型与全量构建骨架

### 阶段二：结构恢复

- 恢复章节层级；
- 合并高置信度跨页段落；
- 解析 HTML 表格的合并单元格；
- 实现三种跨页表格场景；
- 保存表格页码范围和多页 bbox。

完成标准：示例 PDF 第 3-4 页只形成一个表格父对象，并能正确返回两页来源。

### 阶段三：图片处理

- 关联图片、caption、OCR 和附近正文；
- 生成图片检索文本；
- 保存可供 VLM 使用的原图或裁剪图；
- 将表格图片路由至表格处理器。

完成标准：图片问题能够召回图片父对象，并取得实际图片文件。

### 阶段四：多路索引和检索

## 21. 最终验收标准

项目交付时应满足：

1. 每次构建都会覆盖全部旧解析结果和旧索引。
2. 不存在增量处理、文件哈希状态或索引版本切换逻辑。
3. 不存在 `tests/` 目录或测试模块。
4. 正文、表格、图片分别生成父对象和检索子块。
5. 示例 PDF 第 3-4 页跨页表格被表示为一个父对象。
6. 跨页表格答案引用页码 `3-4`，而不是只引用第 3 页。
7. 跨页段落能够在高置信度条件下正确合并。
8. 表格保留表头、合并单元格、单位和脚注。
9. 图片命中后能够取得原始图片或 bbox 裁剪图。
10. 三个 FAISS 索引使用归一化 BGE-M3 向量和内积相似度。
11. 精确数字和关键词同时经过 SQLite FTS5 召回。
12. 检索结果经过 RRF 融合和 Reranker 重排。
13. 计算型表格问题通过 Python 执行确定性计算。
14. 所有答案均可追溯到文档、章节、页码和 bbox。
15. 无法恢复的空表格会导致构建失败，不会被静默忽略。

## 22. 明确不做的内容

- 不做增量索引；
- 不做文件变更检测；
- 不保留历史索引版本；
- 不做索引热切换；
- 不创建测试目录或测试脚本；
- 不将 MinerU Markdown 作为主数据源；
- 不把正文、表格和图片混在同一个切块流程中；
- 不让 LLM 直接承担复杂数值计算；
- 不在证据不足时生成推测性答案。
